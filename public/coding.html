Shadow me
AI-Native Engineer

A scenario, walked step by step. Every decision, every command, every mental model — narrated as it happens.

The Scenario Build a task management system: users can create projects, add tasks with deadlines, assign them, and get email notifications when tasks are overdue.
Phase 00

Before I Touch a Tool

01 Think
Understand the full scope before decomposing anything

Don't touch the keyboard yet. What are the real boundaries of this system? What does "done" actually look like? What are the failure modes nobody mentioned?

I spend 10–15 minutes thinking through the system end-to-end. Not planning how to code it — understanding what it actually is.

Key questions I answer for myself: What does a user do first? Where does email sending live — is it async or synchronous? What happens if an email fails? What does "overdue" mean — midnight of the deadline day? Whose timezone?

02 Decision
Pick the tech stack — and lock it in writing

I decide: Next.js 15 (App Router), Postgres + Drizzle ORM, Resend for email, BullMQ for the notification queue, Vercel for hosting. I write this down immediately.

⚠ Why write it down? If I don't, each agent session will make its own assumptions. One agent uses Prisma, another uses Drizzle. Now I have a conflict I didn't cause.
03 File
Create AGENTS.md — the constitution of the project

This is the first file I create. Before any spec, before any code. Every agent session will read this.

AGENTS.md # Task Management System — Agent Constitution ## Every session: read memory.md first. Append discoveries to memory.md. ## Stack (non-negotiable) - Framework: Next.js 15, App Router, TypeScript strict mode - Database: PostgreSQL via Drizzle ORM (never raw SQL strings) - Email: Resend SDK only (never nodemailer) - Queue: BullMQ + Redis for async jobs - Auth: NextAuth.js v5 - Styling: Tailwind CSS only, no inline styles ## Rules - Never install new packages without asking me first - All DB access through Drizzle schema — never bypass with raw queries - Every API route must validate input with Zod - All errors must be caught and returned as typed responses — never throw unhandled - After every implementation, run: tsc --noEmit && npm run lint - If either fails, fix before marking done ## Timezone rule - "Overdue" = task.deadline < now() in UTC. Store all times in UTC. ## What NOT to do - Do not create new UI components if shadcn has one that fits - Do not add console.log to production code - Do not use 'any' type in TypeScript
Phase 01

Decompose the System

04 Think
Map the system into independent workstreams

What are the natural seams in this system? Where can two agents work without stepping on each other? The answer is always: separate concerns with a defined interface between them.

I sketch the system as a diagram in my head, then on paper. I find four natural workstreams:

🟡 Track A — Core Data Layer
  • DB schema (projects, tasks, users, assignments)
  • Drizzle migrations
  • CRUD API routes
  • Input validation (Zod schemas)
🔵 Track B — Auth + Permissions
  • NextAuth.js setup
  • User model + session shape
  • Permission guards (can this user edit this task?)
  • Protected routes middleware
🟢 Track C — Notification Engine
  • BullMQ queue setup
  • Overdue job scheduler (cron)
  • Email templates (Resend)
  • Retry + failure handling
🟣 Track D — UI
  • Project list + create flow
  • Task board (kanban)
  • Assignment UI
  • Deadline picker
⚠ Track D depends on A and B. The UI needs API routes and auth to exist. So the actual parallel execution is A + B + C simultaneously, then D starts when A and B have stable interfaces — not necessarily finished, just stable enough for D to know what to call.
05 File
Define the interfaces between tracks — before any agent starts

This is the most important step most engineers skip. The interface contract is what lets two agents work in parallel without producing code that conflicts at merge time.

specs/interfaces.md # Interface Contracts ## Task object shape (agreed by Track A + D) type Task = { id: string // uuid projectId: string title: string description: string | null deadline: Date // always UTC assigneeId: string | null status: 'todo' | 'in_progress' | 'done' createdAt: Date updatedAt: Date } ## API routes Track D can assume exist (built by Track A) GET /api/projects → Project[] POST /api/projects → Project GET /api/projects/:id/tasks → Task[] POST /api/projects/:id/tasks → Task PATCH /api/tasks/:id → Task DELETE /api/tasks/:id → void ## Session shape Track D can assume (built by Track B) session.user = { id: string, email: string, name: string }

Now Track D can build the UI calling these routes even before Track A finishes, because both sides have agreed on the contract.

Phase 02

Write the Specs

06 Do Think
Write specs/A.md — with an agent as my thinking partner

I am the architect. I'm not asking the agent what to build — I'm asking it to stress-test what I've already decided. What did I miss? What edge cases will break this?

I open a session with Claude Code. I don't say "plan this for me." I say:

// My prompt to the agent "I'm building the data layer for a task management system. Here's my plan: [paste my outline] Here's the DB schema I'm thinking: [paste schema sketch] I want you to: 1. Identify any edge cases I haven't handled 2. Flag any schema decisions that will cause pain later 3. Ask me questions about anything ambiguous Do NOT suggest a different approach. Work within what I've described."

The agent surfaces three things I missed: cascading deletes when a project is deleted, the index I need for the overdue query, and that BullMQ needs the task ID not the full task object in the queue. I update my plan with those.

specs/track-A.md # Track A: Core Data Layer ## Goal Build the database schema and REST API for projects and tasks. ## Success criteria - All CRUD operations work and return typed responses - Input validation rejects malformed requests with 400 + error message - TypeScript compiles with zero errors - Tests pass for happy path + 3 error cases per route ## Schema projects: id, name, ownerId, createdAt tasks: id, projectId, title, description, deadline(UTC), assigneeId, status, createdAt, updatedAt INDEX on (deadline, status) for overdue query ## Cascade rules - Delete project → cascade delete all tasks - Delete user → set assigneeId = null (do not delete tasks) ## Files in scope src/db/schema.ts src/db/migrations/ src/app/api/projects/route.ts src/app/api/projects/[id]/tasks/route.ts src/app/api/tasks/[id]/route.ts src/lib/validations/task.ts ## Do NOT touch - Auth files (Track B owns these) - Email/queue files (Track C owns these) - Any UI components
07 Parallel
Write specs for B and C — simultaneously

I don't wait for Track A's spec to be perfect before writing B and C. I open two more sessions and do the same process — I architect, agent stress-tests, I update.

Track B spec covers: NextAuth config, the user table additions, session callbacks, and the middleware that protects /app/* routes.

Track C spec covers: BullMQ queue setup, the cron job that runs every hour querying tasks where deadline < now() AND status != 'done' AND notified = false, the Resend email call, and the retry policy (3 attempts, exponential backoff).

✓ Writing three specs in parallel is itself a productivity gain. Each agent session is independent. While one session is thinking, I'm giving input to another.
Phase 03

Implementation — Parallel Execution

08 Do Parallel
Spin up three agents simultaneously on isolated git worktrees

Three terminal windows. Three branches. No file conflicts possible because each track owns distinct files as defined in the spec.

# Terminal 1 — Track A git worktree add ../task-mgmt-track-a feat/data-layer cd ../task-mgmt-track-a claude "Read AGENTS.md and specs/track-A.md then implement" # Terminal 2 — Track B git worktree add ../task-mgmt-track-b feat/auth cd ../task-mgmt-track-b claude "Read AGENTS.md and specs/track-B.md then implement" # Terminal 3 — Track C git worktree add ../task-mgmt-track-c feat/notifications cd ../task-mgmt-track-c claude "Read AGENTS.md and specs/track-C.md then implement"

Now I step back. My job for the next 30–40 minutes is not to code. It's to monitor, unblock, and think about what comes next. I am a director, not an actor.

09 Check
Monitor agents — intervene only when blocked

I cycle between the three terminals every few minutes. I'm looking for one thing: is the agent making a decision that violates the spec or the interfaces contract?

Decision point example
Track B agent asks: "Should I store the user's timezone in the user table?" My answer: "Yes, add a timezone column defaulting to UTC. Update interfaces.md to include it in the session shape."

I update interfaces.md and paste the relevant section into Track A's terminal so it knows about the new column too. This is the coordination work only a human can do across isolated agent contexts.

⚠ What I do NOT do: I don't let the agent decide architectural questions silently. If it's blocked on a decision and just picks something, that decision becomes load-bearing and I won't know it happened. Better to get asked too many questions than too few.
10 Check
Each agent self-verifies before I look at anything

Because AGENTS.md contains the rule "run tsc --noEmit && npm run lint after implementation," each agent does this automatically. I don't review code that has type errors — that's a waste of my attention.

Track A finishes first. It reports: TypeScript passes, lint passes, 12 tests written and passing. Now I do my review.

  • Does the schema match what's in interfaces.md?
  • Are the cascade deletes implemented correctly?
  • Is Zod validation present on every route?
  • Are error responses typed, not thrown?
  • Did it touch any files outside its scope?
  • Does the overdue index exist in the migration?

    • I'm not reading every line. I'm checking the decisions that matter architecturally. Line-by-line review is the AI's job (CodeRabbit / Graphite Agent).

    Phase 04

    Merge, Then UI

    11 Do
    Merge in dependency order, not completion order

    Even if Track C finishes before Track B, I merge in order: A → B → C. Track B's auth middleware depends on Track A's user table. Track C's queue depends on Track A's task IDs. Order matters.

    # Merge order git merge feat/data-layer # Track A — no deps git merge feat/auth # Track B — needs user table from A git merge feat/notifications # Track C — needs task IDs from A

    If there's a merge conflict, I resolve it. Conflicts here usually mean an agent touched a file it wasn't supposed to — that's a spec violation I address immediately and add a rule to AGENTS.md so it never happens again.

    12 Do
    Now start Track D — UI — with full context available

    Track D was waiting for stable A and B interfaces. They're merged now. I write specs/track-D.md, which references the actual API routes and session shape now confirmed in the codebase.

    The UI agent now has the real API to call, real types to import, real session shape to use. It's not building against an assumption. This is why I waited. A UI built on assumed interfaces will need to be rebuilt when reality differs.

    I also add one specific instruction to the Track D prompt:

    "After implementing each UI component: 1. Use Playwright to open the page in a browser 2. Screenshot and verify it renders correctly 3. Check the browser console for JS errors 4. Test the primary interaction (create a task, assign it) Do NOT mark any component done until browser verification passes."
    Phase 05

    Cross-Cutting Concerns

    13 Do
    Run the security subagent across all auth and API code

    This is a specialized agent I defined in .claude/agents/security-reviewer.md. It has one job: find vulnerabilities. It uses Read + Grep tools only — it never writes code, just reports.

    // What the security subagent checks - SQL injection via Drizzle (parameterized queries enforced?) - IDOR: can user A access user B's tasks via /api/tasks/:id? - Auth bypass: are all /api/* routes protected? - Rate limiting: is there anything on auth endpoints? - Secrets in code: any hardcoded API keys? - CORS: is it locked to known origins in production?

    It finds one issue: the PATCH /api/tasks/:id route validates the input but doesn't verify the requesting user owns the project containing that task. Classic IDOR vulnerability. I file this as a fix task and the main agent patches it.

    ✓ This is the value of specialization. A general agent implementing features won't audit for IDOR — it's thinking about making things work, not about how they can be abused. Different mindsets need different agents.
    14 File
    Update memory.md with what was learned

    This happens automatically per AGENTS.md rules. But I also manually add the key architectural decisions made during this session.

    memory.md ## 2026-03-02 - BullMQ requires task ID in queue, not full object — fetch fresh in worker - Cascade: delete project → delete tasks. Delete user → nullify assigneeId - IDOR found on PATCH /api/tasks/:id — fixed, must check project ownership - Overdue query needs composite index on (deadline, status) — added to migration - Timezone: all deadlines UTC, user.timezone for display only

    Next session — tomorrow, next feature, next engineer onboarding — starts with this context loaded. Zero rediscovery cost.

    Phase 06

    Review, Ship, Reflect

    15 Check
    Human review — architecture and business logic only

    I read through the codebase now with fresh eyes. I'm not looking for syntax errors or style issues — the agents and CI handled that. I'm asking one question per file: does this make the right decision for the business?

    Specifically: Does the overdue logic match what a user would actually expect? Does the permission model handle edge cases (what if a project has no owner because the owner deleted their account)?

    I find one business logic gap: when a project is deleted, assigned users should get an email notification their tasks are gone. Not in the spec. I add it as a follow-up task, not a blocker.

    16 Do
    Open small, stacked PRs — not one giant PR

    A 2,000 line PR is a rubber-stamp PR. Nobody actually reviews it. Four 200-line PRs get real review.

    I open four PRs in order:

  • PR 1: DB schema + migrations (Track A foundation)
  • PR 2: API routes + validation (Track A routes)
  • PR 3: Auth setup (Track B)
  • PR 4: Notification queue + email (Track C)
  • PR 5: UI components (Track D)

    • Each PR is small enough to review in 10 minutes. CI runs on each. They're stacked — each one merges into the next, not into main directly.

    17 Reflect
    Update AGENTS.md with what to do differently next time

    The IDOR vulnerability tells me my security spec was too vague. I add a new rule to AGENTS.md:

    ## New rule added after this session For every PATCH and DELETE route: verify the requesting user has permission on the parent resource, not just the resource itself. Example: to edit a task, verify user owns the project, not just the task.

    This rule now exists permanently. The next feature, the next agent, the next session — this mistake can never happen again. This is the compounding effect. Every correction makes the system permanently smarter.

    The mental model shift: A traditional engineer writes code. An AI-native engineer designs systems that write code. The AGENTS.md, the specs, the interfaces contract, the memory.md — that's the real work. The code is the output of the system you built, not the thing you built.

    Every decision you wrote down, every rule you added to AGENTS.md, every entry in memory.md — those compound. In three months, you have an AI development environment that knows your codebase, your standards, your past mistakes, and your architectural preferences. Nobody else has that. It's yours.
